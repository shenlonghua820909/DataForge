# 数据清洗（ODS → DWD）商用生产级就绪度评估

> 评估对象：`pages/15-data-cleaning.html`、`assets/cleaning.js`（4,584 行）、`assets/integration-data.js`、`assets/file-parse.js`
> 评估方式：全量源码核查（逐段读码 + 全仓检索），不采信文档中的自述；结论均可按给出的行号复核
> 评估时点：2026-09-21

## 结论

**逻辑闭环分段成立。** 「配置规则 → 前端执行 → 预览 / 质量指标 → 生成 SQL → 保存任务与版本」这一条链是真实跑通的，不是写死的假交互 —— 这一点比多数原型扎实，规则引擎、列计划、SQL 生成、撤销栈都是真实现。

**生产级就绪度：未闭环，且缺口是整个平台层。** 支撑生产运行的六件事目前一件都没有：真实数据、执行引擎、调度、存储、权限、审计。差距不在「再补几个功能」，而在「这套东西现在跑在浏览器内存里，没有任何一个地方可以真正落到生产集群上」。

判断依据是三条硬事实：① 源数据是**源码里硬编码的 12 行**；② 数据源**没有任何连接信息**，02b 的「开始测试」是模拟过程；③ 全仓 **0 处网络请求**，没有后端。

## 三、三个架构级风险

这三条比功能清单更要紧 —— 功能可以补，架构选错了要返工。

### 3.1 双实现：预览引擎与 SQL 生成器是两套独立代码

预览结果由 9 个 `step.run()`（JS）算出，SQL 由 `genSQL()`（372 行）另外拼出。同一套语义、两处实现。

后果不是理论推演：**已有实证** —— 码值映射同一字段配两组对照时，`run()` 遍历全部、`genSQL()` 只取第一条，**预览与 SQL 静默不一致**（2026-09-21 已修复：抽出 `effectiveMaps()` 作为预览与 SQL 共用的唯一判据）。**但要注意修复的边界**：这一修只堵住了「同字段多组」这一条缝，双实现本身仍在 —— 规则条目继续增长，同类漂移还会从别的缝里冒出来（这正是下面这条分界的意义所在）。

生产级做法的分界在这里：DataWorks 那类产品里，预览就是**在真实引擎上跑 `LIMIT 200`**，不存在第二套实现。只要保留两套独立实现，这类漂移会随规则条目数增长，且**不报错**——最坏的一种缺陷形态。

### 3.2 数据是假的，性能与边界全都测不到

12 行模板 + 等比例放大意味着：

- 看不到真实脏数据分布（真实源库的脏数据形态与比例不会这么均匀）
- 测不到规模问题（128 万行的去重、关联、排序在浏览器里跑不动）
- 测不到边界（分区、增量、超长字段、控制字符、编码、并发写入冲突）

### 3.3 没有可以落地的执行面

没有执行引擎、没有调度、没有存储 —— 配置好了也没有地方去跑。这是原型与生产之间最本质的一条分界。

## 五、落地路径建议

### 阶段 0：技术验证 —— 把「假」变「真」

目标：证明「生成的 SQL 能在真实引擎上跑出正确结果」。

1. 接一张真实业务表（不要一次接全套）
2. 生成的 SQL 提交到真实引擎执行，预览改为 `LIMIT 200` 真采样
3. 消灭双实现：预览结果 = SQL 执行结果

验收标准：同一份配置，预览结果与 SQL 执行结果**逐行一致**。

### 阶段 1：最小可用生产（MVP）

1. 数据源管理（连接 + 测试 + 元数据同步）
2. 调度对接（选一个调度器）+ 依赖编排 + 日调度跑通
3. ODS / DWD 真实落表与分区
4. 质量门禁真实阻断 + 告警通知
5. 认证与权限（按项目隔离）
6. 任务实例与运行日志

验收标准：一个业务域（如流通借阅）的 ODS → DWD 全链路每天自动跑通，失败有告警、异常可追溯。

### 阶段 2：完整生产

血缘与影响分析、质量报告与对账、补数与重跑、多租户隔离、监控大盘、SLA。

## 六、一句话回答

**现在是一个「规则引擎与交互范式已充分验证、但运行面完全缺失」的原型。** 它的价值在于把「图书馆数据清洗需要哪些规则、交互怎么做才顺手」这件事问清楚了；要上生产，需要补的是从接入、执行、调度到治理的一整条链路，而不是在现有页面上继续加功能。
